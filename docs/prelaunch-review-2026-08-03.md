## （1）第一次使用會卡在哪裡

依實際程式碼走過首次使用流程，依「會不會直接中斷任務」排序。

### A. 出生地打「臺北」查無結果 —— 會直接中斷任務

清單存的是「台北市」，比對用 `indexOf` 純字面比對，而「臺」是身分證與戶籍謄本上的
官方用字。實測 `臺北`、`臺中` 皆回傳空陣列。城市選不到就無法生成星盤，整個星盤、
人生主題、運勢、合盤全部進不去，而畫面只說「查無此城市」，使用者不會想到問題出在
一個異體字。

**已修**：`normalizeCityQuery()` 正規化 臺→台、巿→市、去空白、大小寫折疊。
`臺北` / `台北` / ` 台北 ` / `臺北巿` / `TAIPEI` 現在都指向台北市。

### B. 真的不在清單裡時，沒有下一步

清單 93 個城市。台灣 22 縣市全收，但海外小城市必然找不到，原本的提示只是叫使用者
換個關鍵字再試——如果城市根本不在清單裡，換幾次都一樣。

**已修**：明講清單規模，並給出可執行的替代方案：選同時區最近的大城市，同時說明為什麼
可接受（同時區不影響行星星座，只有上升與宮位差幾分鐘）。

### C. 「複製給 AI 解讀」複製完就沒了

按鈕變成「已複製！」，但沒有告訴使用者要貼到哪裡。第一次用的人手上握著三萬字的
提示詞，不知道下一步。

**建議（未修）**：複製成功後在按鈕下方顯示一行「已複製，貼到 ChatGPT／Claude／Gemini
的對話框送出即可」，並列出三個連結。

### D. 星盤分頁的分頁列一次露出四組控制

`認識自己`、`人生主題`、`近期運勢 ▾`、`進階分析 ▾` 四個同層級按鈕並排，展開後最多
再多八個。第一次進來的人沒有依據判斷該點哪一個。目前靠「不知道從哪開始？查看功能說明」
這行小字補救，但它在分頁列下方、字級 11px。

**建議（未修）**：首次進入且尚無命盤時，直接把「認識自己」設為預設並隱藏其餘分頁，
等使用者生成第一張盤之後再顯示完整分頁列。

### E. 人生主題要點三層才看得到結果

選主題 → 選題目（最多 3）→ 按「產生專題分析」。中間沒有任何內容，空白等待。

**建議（未修）**：選定主題後先顯示該主題的一段總覽（不需選題目就能算），
把「產生專題分析」變成加深而非解鎖。

### F. 占卜精靈第 3 步的自由文字題

`maxlength="300"` 的 textarea，第一次用的人不知道該寫多細。目前有 placeholder 與
`updateQHint()` 提示，屬於可接受範圍。

**建議（未修）**：提供 2–3 個可點選的範例問題直接填入。

**加權總分（等權）：74 → 90**

### 未處理項目

- **CSP**：GitHub Pages 不能設 HTTP header，只能用 `<meta http-equiv="Content-Security-Policy">`。因為大量使用 inline style 與 inline event handler，導入 CSP 需要 `unsafe-inline`，防護價值有限，且一旦寫錯會整站白畫面。建議暫緩。
- **Subresource Integrity**：Google Fonts 的 CSS 網址內容會依 User-Agent 變動，無法固定 hash。
- **CITY_LIST 只有 93 個城市**：海外小城市仍會落空，已用「同時區最近大城市」的說明降低衝擊。

### 建議執行順序

1. **方案 2**（92%）—— 效益最高、風險最低，縮圖已經存在，只是沒被用在抽牌畫面。
2. **方案 1**（80%）與 **方案 3**（80%）—— 都是純資源調整，不動邏輯。
3. **方案 5**（76%）—— 要調整 sw.js 的 CORE 清單與寫入時機，需測試離線行為。
4. **方案 4**（56%）—— 效益可觀但拆分 357KB 單檔風險高，建議等前四項做完再評估是否仍有需要。

執行方案 1、2、3、5 之後，首屏 gzip 傳輸量預估從 149 KB 降到約 **120 KB**，
抽牌流程圖片流量減半，首次進站背景流量減少 686 KB。加上本輪已完成的影片修正，
效能面向推估可達 **93–95**。

方案 4 不建議在上架前執行——它是四個方案裡唯一會動到既有架構的，而
`AGENTS.md` 明列 `js/app.js` 為高風險檔案。
