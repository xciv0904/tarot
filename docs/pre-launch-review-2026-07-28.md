## （1）第一次使用會卡住的地方

以「完全沒用過塔羅、也沒看過這個網站」的人走一次完整流程，卡點依嚴重度排列。

### A. 會讓人以為「網站壞了」的死路（已修）

**A1. 「更多 → 新手使用指南」點下去完全沒反應**

`openBeginnerGuide()`（`js/app.js:1334`）的做法是把 `state.homeTourDismissed` 設回 `false`、再 `go('home')`。但 commit `1bd3866 feat: simplify navigation for first-time users` 把首頁裡 `h += renderHomeTourCard();` 那一行刪掉了，卻沒有一併處理這個入口。結果是：`renderHomeTourCard()` 這個 24 行的函式定義還在、`homeShowTour()` 也還在，但全站沒有任何地方呼叫它們。

對第一次使用的人來說，這是最糟的一種卡點——他主動去找「新手使用指南」，代表他已經卡住了，而這顆按鈕只會把他丟回首頁，畫面一模一樣。

> **改善方案｜已實作**：在 `renderHome()` 的三顆入口按鈕下方接回導覽卡（`!state.homeTourDismissed` 時顯示），關掉之後改顯示一行「新手導覽 · 再看一次」，讓 `openBeginnerGuide()` 與 `homeShowTour()` 兩條路都有畫面回應。

**A2. Step 3「想深入了解的面向」整區消失**

`renderFocusAreaPicker()`（`js/app.js:1598`，約 40 行）在 commit `97a291c` 之後失去唯一的呼叫端。連帶失效的還有 `computeDefaultFocusOptions()`、`wizToggleFocus()`、`wizToggleFocusExpand()`，以及 `state.wizFocusSel` / `wizFocusExpanded` / `wizFocusLimitHit` 三個 state 欄位。

更關鍵的是 `copyForAI()`（`js/app.js:3503`）仍然在讀 `state.wizFocusSel[state.category]` 來組裝 AI 提示詞——因為 UI 不存在，這個陣列永遠是空的，「複製給 AI 解讀」送出的提示詞就少了使用者最想聚焦的面向。這是一條從資料層（`reading-data.js` 的 `topicQuestionConfig.focusGroups`）到輸出層都完整、只斷在 UI 一行的功能鏈。

> **改善方案｜已實作**：在 Step 3 的子問題選擇器之後、自由輸入問題之前接回 `renderFocusAreaPicker()`。順序是「先選面向 → 再寫問題」，符合由粗到細的填答直覺。

### B. 使用者填得完、但填得很累的地方

**B1. Step 3 一頁塞了五種輸入**

現在的 Step 3 依序是：對象輸入框 → 解讀來源選擇（牌／牌＋星盤）→ 子問題下拉 →〔面向複選〕→ 範例問題 chips → 自由輸入 textarea →〔雷諾曼另有時間範圍〕。第一次來的人在同一個畫面上要做 5–7 個決定，而且每一項都是「選填」。

實測下來最容易發生的是**放棄輸入直接按下一步**——這不是壞事（系統支援「未填寫，將以通用方式解讀」），但等於整套個人化解讀白做了。

> **改善方案｜建議（未實作，屬視覺改版）**：把「選填」三個字換成「填了會更準」的正向框架，並在 Step 3 頂端加一行「以下都可以跳過，但填越多解讀越貼近你」。成本低、不動結構。

**B2. 「快速占卜／直接抽一張牌」藏在首頁「其他功能」摺疊區裡**

首頁一級入口有三顆：今天需要一點指引／我有一件事想問／我想更了解自己。想「隨便抽一張看看」的人，要先展開「其他功能」才找得到 `quickDraw()`。但首頁最上方那顆「今天需要一點指引」其實只是捲動到今日一牌，兩者功能高度重疊，新使用者不容易分辨差別。

> **改善方案｜建議**：合併或明確區分這兩個入口（見第 2 節 U3）。

**B3. 星盤分頁要填三段資料才有任何回饋**

`renderBirthInputForm()` 要求出生日期＋時間＋城市三項齊全才會啟用「生成星盤」。已有「已完成 n / 3 項」的進度提示（做得不錯），但在填完之前，畫面上完全沒有任何預覽或誘因。對還在觀望的人，這是一道 3 欄位的付費牆感。

> **改善方案｜建議**：只填出生日期就先給出太陽星座一行摘要（不需要時間與地點），把「還要填 2 項」變成「你已經拿到一點東西了」。

**B4. 塔羅 vs 雷諾曼的說明藏在 Step 1 的 `<details>` 裡**

`renderTarotLenormandGuide()` 內容寫得很好，但要點開「想自己選牌組？」才看得到。不知道差別的人，恰恰是不會去點那一行的人。

### C. 無障礙與操作細節（已修）

| 位置 | 問題 | 處理 |
|---|---|---|
| `renderReading()`「在牌典查看這張牌」 | `<span onclick>`，Tab 走不到、讀屏不念 | 改 `<button>` |
| `renderHistory()` 歷史紀錄卡 | `<div onclick>`，鍵盤完全無法開啟 | 加 `role="button"` `tabindex` `onkeydown` |
| `renderNav()` 底部導覽 | 目前分頁只用顏色深淺表示 | 加 `aria-current="page"` |

### 3.2 已確認為「無問題」的項目

- **XSS**：`esc()`（`app.js:124`）覆蓋 `& < > " '`，所有進入 `innerHTML` 的使用者輸入（`state.question`、`state.target`、歷史紀錄的 `typeLabel` / `summary` / 卡片欄位）都有經過。全站 `innerHTML` 只有 8 處，皆為框架層賦值。
- **無外部請求**：無 `eval`、無 `new Function`、無 analytics、無 API 呼叫；唯一的外部資源是 Google Fonts。
- **出生日期驗證**：`validateBirthDate()` 對年（1900–2100）、月、日（含每月實際天數）、時、分逐項檢查，且已處理「空字串時間被 `parseInt('')||0` 靜默當成 00:00」這個歷史陷阱。
- **輸入長度**：`target` 80 字、`question` 300 字，`maxlength` 與 JS `slice()` 雙重限制。
- **中文輸入法**：城市搜尋框刻意避開整頁 `render()`（`renderCityLiveBlock` 的註解寫得很清楚），只更新旁邊的建議清單，注音組字不會被打斷。這一點做得比多數同類專案好。
- **Golden 回歸**：基準雜湊 `9b2247a368651a61` 修改前後完全一致，代表 648 筆解讀內容零漂移。

## （4）把效能推到 93 分以上：五個方案

| `js/data/card-images.js` | 4,812 B | 672 B | ✅（今日一牌） |

---

**P1｜`reading-data.js` 改為按需載入（加權 86.0）**

`reading-data.js` 是 165KB / gzip 53KB 的牌義與題庫資料，只有「占卜」與「牌典」分頁用得到，首頁的今日一牌只需要 `card-images.js` 與 `app.js` 裡的 `TAROT` 陣列。做法完全比照 `index.html` 現成的 `ensureAstrologyDataLoaded()`，在 `go('reading')` / `go('library')` 時才載入。

- 預估效益：首屏 gzip 少 53KB（−18.6%），解析工作量同步下降
- 風險點：`app.js` 頂層有 `TAROT.forEach(...)` 掛 `RICH` 資料的初始化（`app.js:106`），需要一併搬進載入完成的回呼
- **建議**：先做這個。有現成的載入器可以照抄，是投報率最高的一項

**P2｜抽牌與結果畫面改用縮圖（加權 86.0）**

`assets/cards/thumbs/` 已經存在（114 張、3.3MB、平均 29KB），但目前只用在 `app.js:3871` 的牌典網格。抽牌結果畫面每張牌的顯示寬度是 26–46%（手機上約 90–160px），卻載入平均 65KB 的全尺寸圖。凱爾特十字一次要抽 10 張＝650KB，改用縮圖只要 290KB。

同時建議補上 `width` / `height` 屬性，消除翻牌時的 CLS。

- 預估效益：抽牌畫面圖片流量減少 55%，凱爾特十字／大牌陣最有感
- 風險點：需確認縮圖解析度在高 DPI 手機上不會糊；建議先目視比對 2–3 張
- **建議**：做。資產已經在 repo 裡，只是沒用上

**P3｜從 `app.js` 切出星盤進階功能（加權 81.0）**

`app.js` 裡合盤（`renderSynastry` 起）、二次推運（`computeProgressedChart` 起）、28 宿（`XIU_DEFS` 起）、流年運勢（`renderHoroscope` 起）合計約佔 40% 的行數，而這些功能只有在使用者已經生成星盤、並主動切到對應分頁時才會用到。

- 預估效益：首屏 JS 從 gzip 286KB 降到約 190KB（−34%），是唯一能單獨把效能推過 90 分的方案
- 風險點：這幾塊與 `state` 和主流程共用大量輔助函式（`astroNormDeg`、`pad2`、`fallbackCopy`、`renderPersonaPicker` 等），拆分時要精確劃出邊界。`AGENTS.md` 明列「Extracting old code from `app.js` should be a separate, tested task」，**必須單獨開一次任務、單獨驗證**，不要和其他改動混在一起
- **建議**：做，但獨立一次 commit，前後都跑完整 `npm test` 並手動走過合盤／推運／28 宿三條路徑

**P4｜自架字型子集（加權 66.0）**

目前仍依賴 `fonts.googleapis.com`，即使已改為非阻塞，仍有 DNS + TLS + 兩段請求（CSS → woff2）的往返成本。中日韓字型 Google 會自動切成上百個 unicode-range 分片，實務上表現其實不差。

- 預估效益：省下第三方往返，但幅度遠小於 P1–P3
- 風險點：自行子集化中日韓字型，容易漏字（牌名、宿名、星座符號都是低頻字），且要自行處理授權
- **建議**：排在最後，或直接放棄。本次已完成的「移除未使用家族 + 非阻塞載入」已經拿到這條線上八成的效益

**P5｜`render()` 改為分區更新（加權 65.0）**

現在每次互動都是 `view.innerHTML = renderXxx()`，整個畫面的 DOM 全部重建。在星盤分頁（數千個節點）點一個摺疊區，成本相當高，會反映在 INP 指標上。

- 預估效益：改善互動延遲，但不影響首次載入分數
- 風險點：**這是本清單中風險最高的一項**。目前所有互動函式都假設「呼叫 `render()` 之後畫面一定是全新的」，改成局部更新會牽動幾百個呼叫點；而且 `renderCityLiveBlock` 的註解已經記錄過一次「整頁重繪打斷注音組字」的教訓，動這裡容易再踩一次

## （6）解讀文案品質排查與優化

用實際的解讀引擎產生 4,148 段輸出（8 分類 × 各子問題 × 8 組抽牌 × 2 種牌組，加上 78+36 張牌正逆位的五個欄位）當作語料，量化檢查。

### 6.1 找到的問題與修正

**問題 1｜中文句子裡混用半形逗號 — 720 處**

`reading-rich-data.js` 有 716 處、`app.js` 有 4 處。使用者直接看得到，例如：

> 這次牌面透露的訊息是，雙方有事情未坦誠溝通**,**情感停留在表面。

只在「前後都是中文字」時替換成全形，不會動到 JSON 語法的逗號。修正後 0 處。

**問題 2｜句尾標點時有時無 — 佔輸出的 63%**

牌義資料裡有 46% 的長句沒有句號。組合出來的結果就是同一個面板上，一行有句號、一行沒有：

> 核心結論：從你目前抽到的牌來看，在感情與其他生活重心間取得平衡　← 沒有句號
> 核心結論：這次牌面透露的訊息是，隱瞞的事情或誤解逐漸被釐清。　← 有句號

沒有直接改資料——那些句子在組裝過程中還會被接到別的句子中間，直接加句號會產生「。，」。改成在輸出的最後一關用 `polishSentence()` 統一補。修正後 4,148 段全部有正確句尾標點，且 0 處標點組合錯誤。

**問題 3｜說了等於沒說的罐頭句 — 315 次**

最嚴重的是「中性」語氣的 `trend` 欄位，三句話都在說「我不知道」：

> 發展走向還在醞釀中，順與不順都各有一些，需要再觀察一段時間
> 目前處於過渡階段，趨勢尚未完全明朗，建議保持彈性
> 事情的走向取決於接下來雙方的互動，暫時沒有絕對的定論

這三句合計佔 `trend` 出現次數的 31%。改寫原則是：中性不等於不知道，中性是「兩邊都有可能，而這是決定的關鍵」：

> 關係停在不上不下的位置，通常是有句話還沒說出口，說了才會動
> 兩邊都還在觀望，誰先把自己的期待講清楚，走向就往誰的方向偏

愛情與事業兩個分類的 `trend` / `favor` / `risk` / `action` / `timing` 中性語氣池全部重寫（家庭、財運等分類原本就寫得夠具體，未動）。星盤側同樣毛病的兩個中性語氣池也一併修正。填充語出現次數 315 → 0。

**問題 4｜大牌的「玄學廢話」降級句**

塔羅大牌本來就不描寫「某一個人」，原本的降級句用玄學詞填滿版面：

> 這個人可能帶有某種鮮明的個人風格，氣質難以用單一詞彙概括
> 給人的感覺超出一般日常互動的份量，帶著某種命定般的氣場
> 個性帶有某種鮮明的主軸，相處模式可能不落於一般常規

七個描述軸心（年齡／外貌／個性／職業／經濟／家庭／相遇場合）的大牌降級句全部改寫成誠實說明：

> 這張是大牌，畫的是處境而不是長相，外型這一項牌面給不出具體描述
> 職業這一項牌面沒有指向特定行業，直接問或觀察會比從牌面推測準確
> 大牌顯示家庭對這個人影響很深，但沒有指出是什麼事，不要自己補劇情

說「牌面給不出這一項」比說一堆聽起來很玄卻無法驗證的話更有用，也降低使用者過度解讀的風險。

**問題 5｜綜合解讀每次都用同一句收尾**

`CAT_ADVICE` 每個分類只有兩句，而且用語氣直接索引，所以同一分類同一語氣永遠是同一句結尾——連抽十次牌，最後一句都是「整體而言，真誠表達你的感受，關係會朝好的方向開展。」

改成三種語氣各三句（共 72 句），再用抽到的牌做雜湊挑句：同一組牌結果仍然可重現，不同組牌就會換句。結尾句從 8 種變成 48 種，單句最高占比 23% → 7%。

**問題 6｜組出不通順的句子**

`'牌面首先呈現的是一位較' + tag + '的人'` 這個樣板，遇到兩段式形容詞會產生「一位較**氣場順遂、給人好感**的人」這種讀不通的句子。改成把形容詞放進引號：

> 從代表牌看，對方給人的感覺是「情感豐富、容易被打動」；同一張牌也提醒你⋯⋯

**同一次解讀內部的重複**：檢查 480 組完整解讀的欄位兩兩比對，10 字以上的重複片段 **0 組**——重複問題主要出在「不同次抽牌之間」，已由問題 3、5 處理。

## （7）星盤側文案排查與優化

用 4 張真實星盤跑過所有星盤畫面（本命落點、額外本命點、各分類解讀引擎、合盤、二次推運、二十八星宿、每日／週／月／年運勢、人生主題），加上 Golden 快照的 648 筆答案，合計 **5,863 段輸出、18 萬字**當語料。

### 7.1 檢查後確認「沒有問題」的項目

| 項目 | 實測 | 判定 |
|---|---|---|
| 籠統填充句 | 全部 648 筆答案中只有 9 次（適時 3、適度 4、需要時間 2） | 很乾淨，不需處理 |
| 跨答案重複 | headline 47% 獨特句、summary 35%、detail 42%；單句最高占比僅 1–3% | 多樣性足夠 |

第四點值得說明：我一開始以為合盤、推運、運勢三個畫面「整片都是術語」，實際檢查後發現不是——

### 7.2 找到的問題與修正

**問題 1｜60% 的答案，結論句和分項說明在講同一件事**

人生主題卡片的結構是「題目 → 結論 → 分項（各有標籤）→ 提醒」。但分項的內文常常只是結論的一段殘句：

> **結論**：容易被能展現**美感、協調與關係經營**、互動節奏講究平衡與感受的人打動。
> **［容易被什麼特質吸引］** 美感、協調與關係經營
>
> **結論**：衝突後先**恢復熟悉感、歸屬感與穩定回應**，再運用同理、照顧與察覺氣氛把問題說清楚。
> **［衝突後的第一步］** 第一步是恢復熟悉感、歸屬感與穩定回應

**問題 2｜12% 的分項在重述自己的標籤**

標籤已經寫「衝突後的第一步」，內文又從「第一步是⋯⋯」開始；標籤寫「適合的相處模式」，內文開頭是「相處需要⋯⋯」。全站 300 條。

**問題 3｜1,308 條分項全部沒有句尾標點**

結論、摘要、提醒都有句號，只有分項沒有。同一張卡片上，上面那行有句號、下面幾行沒有。

### 7.3 修正方式與一個關鍵限制

修正時碰到一個限制：`validateNatalTopicContent()` 的 `min_answer_targets` 檢查要求分項數量不得少於題目宣告的 `answerTargets`，所以**不能直接把重複的分項從資料裡刪掉**。因此拆成兩層處理：

**資料層**（`buildQuestionContent` 的最後一關，`polishNatalAnswer`）
- 內文開頭如果在重述自己的標籤（開頭短語與標籤有 2 個以上共用字），就把它拿掉
- 拿掉後剩餘內容不足 6 字則維持原樣——寧可留贅字，也不要留半句話
- 統一補上句尾標點

**顯示層**（`visibleNatalDetails`）
- 分項內文如果整句都已包含在結論裡，畫面上不顯示這一列（它不提供任何新資訊）
- 「複製給 AI」套用同一個過濾，避免提示詞裡同一句話出現兩次
- 資料本身完整保留，`min_answer_targets` 檢查與歷史紀錄不受影響
- 實測 648 張卡片**沒有任何一張**會因此變成完全沒有分項，程式仍加了保險判斷

另外把合盤摘要唯一沒解釋的術語補上說明：

> 舊：這份「戀愛／伴侶」合盤共有 23 組緊密**相位**，其中 10 組是和諧相位、11 組是挑戰相位。
> 新：這份「戀愛／伴侶」合盤裡，兩人的星盤有 23 組明顯的互相牽動（占星上叫「**相位**」），其中 10 組是彼此加分的、11 組是需要磨合的。
