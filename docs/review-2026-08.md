## （1）第一次使用會卡在哪裡

以「沒用過塔羅、也沒看過星盤」的人從首頁進站為前提，逐段走過流程後找到的卡點。

### F1　首頁沒有告訴新手「先做什麼」，反而先把他推走
首頁底部寫著「初次接觸塔羅嗎？建議先到底部導覽列的『牌典』認識大阿爾克那 22 張牌，再回來開始占卜」。
這句話把想試試看的人擋在門外——要先讀完 22 張牌才有資格占卜。

**改善**：把它改成占卜後的延伸建議，首頁只留一個明確動作（抽一張牌）。牌典的價值在「抽完想深入」時才成立。

### F2　精靈第一步的資訊量最大
一屏之內要處理：9 個分類卡片、牌組選擇、牌組差別說明、下一步按鈕。而分類卡片本身是雙行（標題＋說明）。

**改善**：牌組已經有預設值（塔羅），把它降級為結果頁可切換的選項；第一步只留分類。

### F3　不知道出生時間的人會在星盤第一關卡住
`validateBirthDate()` 會擋下缺少時分的輸入，「不確定時間」的勾選框在時間欄位下方，要先看到才知道有解。

**改善**：時間欄位獲得焦點時就顯示「不知道時間？」的提示連結，而不是等驗證失敗才說。

### F4　結果頁很長，而且分不出哪一段才是答案
渲染後的 HTML 約 25KB。目前的順序是牌卡 → 語氣 → 按鈕 → 直接回答 → 整副牌的走向 → 綜合觀察 → 每張牌 → 延伸問題。
「直接回答」被壓在按鈕列後面，第一次用的人會從上往下讀完才知道結論在中間。

**改善**：「直接回答」上移到牌卡正下方；語氣與按鈕列移到底部。

### F5　「複製給 AI」不知道複製了什麼、要貼到哪
按鈕文字是「複製給 AI」，按下去只有一個「已複製」提示。使用者不知道內容有多長、包含哪些資料、下一步該開哪個網站。

**改善**：複製後展開一段預覽（前 3 行 + 共幾字），並列出三個直達連結。星盤那邊已經有連結，塔羅這邊沒有。

### F6　資料只存在這台裝置，但使用者不知道
沒有帳號、沒有伺服器。清瀏覽器資料、換手機、換瀏覽器都會全部消失。
**已修**：「更多」分頁新增「你的資料」區塊，說明這件事並提供匯出／匯入。

### F7　破壞性操作用 browser confirm()
「清除所有紀錄」「刪除命盤」「重新輸入」「刪除朋友存檔」四處都是 `confirm()`。
**已修**：全部改為畫面內兩段式確認。細節見第（3）節 A1。

### F8　牌典 114 張，沒有起點
有「22 天大牌之旅」，但入口在記憶心法頁籤裡面，第一次進牌典不會看到。

**改善**：牌典首屏放一張「不知道從哪開始？」卡片，直接連到 22 天計畫。

## （3）上架前審查：修正與前後評分

### 這一輪實際修掉的問題

**A1　破壞性操作可能在沒有確認的情況下執行（嚴重）**
四處刪除／清除都寫成：

```js
try { if (!confirm('...')) return; } catch (e) {}
```

`confirm()` 被瀏覽器抑制時回傳 false（安全），但**丟出例外時 catch 會吞掉它，程式繼續往下走，資料就被刪了**。
已全部改為兩段式：第一次點擊只上膛並在畫面上長出說明與兩個按鈕，第二次才執行。`multi-chart-regression` 新增「第一次點刪除不會真的刪掉」。

**A2　沒有錯誤邊界（嚴重）**
整個畫面是 `view.innerHTML = render()` 一次寫進去的。render 途中丟例外＝畫面停在上一個狀態或空白，而且沒有任何訊息。
已加入 `error` 與 `unhandledrejection` 監聽，出錯時底部顯示說明、重新載入按鈕與可展開的技術細節，並明講「資料都還在這台裝置上」。資源載入失敗（`e.error` 為空）不觸發，那些各自有降級處理。

**A3　沒有資料出口（嚴重）**
localStorage 是唯一的家，沒有匯出。清除按鈕不可復原。
已加入匯出備份（JSON）與從備份還原。還原只接受 `APP_STORAGE_KEYS` 白名單內的 key、只接受字串值、並檢查 `format` 欄位——備份檔被改過也塞不進任意內容。

**A4　沒有 CSP**
已加入 meta 版 CSP：`object-src 'none'`、`frame-ancestors 'none'`、`form-action 'none'`，連線目的地只有 Google Fonts。
`script-src` 必須保留 `'unsafe-inline'`（整站互動是 onclick 屬性），真正的防線是所有插入畫面的字串都經過 `esc()`。

**A5　`reassignImages()` 是死碼**
全專案零呼叫點，牌圖其實在 `reading-data.js` 載入時就指派好了。留著只會讓下次除錯的人走冤枉路。已刪除。

**A6　Service Worker 每次改版清空全部牌圖**
`activate` 刪掉所有非當前版本的快取，圖片跟程式共用同一個快取——這一輪推了六次版本，等於清空 228 張圖六次；重抓時 assets 分支又沒有 catch，逾時就是永久破圖。
已分離 `mystic-assets-v1`（不隨版本清空）＋失敗重試＋`<img onerror>` 退回牌名方塊。

## （4）把效能推上 93% 的五個方案

先講現況數字，避免方案建立在猜測上：

| 項目 | 現況 |
|---|---|
| 首次載入 JS（gzip） | **192KB**（app.js 140、reading-data 37、reading-interpretation 6、card-images <1、index.html 8） |
| 延後載入 | astro-advanced 608KB、astronomy-engine 116KB、astro-charts 76KB、astrology-* 資料約 250KB |
| 牌圖 | 全圖平均 65KB × 114 張（11MB）；縮圖平均 29KB × 114 張（3.4MB） |
| 字型 | 3 個家族、9 個字重，全部從 Google Fonts |
| 建置流程 | 無。沒有壓縮、沒有 tree-shaking、沒有 hash 檔名 |

| # | 方案 | 必要性 | 功能性 | 有感 | 易維護 | 低風險 | **總分** | 預估效果 |
|---|---|---|---|---|---|---|---|---|
| P1 | 牌典縮圖再縮一級（300px→160px，牌典格狀清單用） | 90 | 85 | 90 | 95 | 95 | **91.0** | 牌典首屏由 3.4MB 降至約 1MB |
| P2 | 字型收斂成 2 家族 5 字重，並自架 woff2 子集 | 85 | 80 | 85 | 80 | 85 | **83.0** | 移除 Google Fonts 的第三方連線與 FOUT，首屏渲染提前約 200–400ms |
| P3 | 把 app.js 依分頁切開（占卜／牌典／學習／歷史） | 90 | 90 | 80 | 65 | 60 | **77.0** | 首次載入 gzip 192KB → 約 110KB |
| P4 | 加入最小建置步驟（esbuild minify + 檔名 hash） | 80 | 90 | 75 | 70 | 65 | **76.0** | gzip 再降 25–30%，且能移除 SW 版本號手動維護 |
| P5 | 牌圖改 AVIF，webp 作為 fallback | 60 | 75 | 70 | 70 | 80 | **71.0** | 圖片再降 30–40%，但需要雙份檔案與 `<picture>` |

### 建議路徑

**先做 P1 + P2**，合計 174 分、風險都低，兩者都不碰 JavaScript 邏輯，做完預估效能可到 **85–88**。

**要越過 93 必須做 P3 或 P4**，兩者都是結構性改動：

- P3 的風險在於全站是 classic script、共用全域函式，切檔要先確認跨檔呼叫的邊界。目前 `app.js` 有 456KB 單檔，切開之後跨檔依賴會變成隱性契約，需要一支「載入順序」測試守住。
- P4 引入 node 建置後，現在「改完直接推、GitHub Pages 直接serve」的流程會消失，而這個專案的每一次修正都靠這條路徑。

**我的建議**：先做 P1、P2 拿到 85–88，然後做 P4 而不是 P3。P4 一次解決壓縮與 SW 版本號兩件事，而且不需要重排任何程式結構；P3 的收益與 P4 重疊，但要動的東西多得多。

### 這份報告沒有涵蓋的

- **沒有真跑過 Lighthouse**。沙箱裝不了 Chromium，上面所有效能數字都是檔案體積與載入結構的推算，不是實測分數。要確認請在你的 Chrome DevTools 跑一次 Lighthouse（行動裝置模式）。
- **占星計算的準確度沒有測試**。現有 Golden 測的是「解讀結構與文字」，不是天文計算本身是否正確。要驗證需要一組已知星曆的對照資料。
- **多命盤、上升區間、合盤、牌典、題庫分類全部沒有在真實瀏覽器點過**。它們都有回歸測試，但測試驗的是輸出字串，不是實際互動。
